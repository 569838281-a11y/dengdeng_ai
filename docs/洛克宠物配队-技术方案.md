# 洛克宠物自动配队技术方案

本文只定接下来的改法，不改现有代码。当前仓库里的知识库、三个助手和重合选队逻辑保持原样，作为老师链路。后面的工程按本文拆开实现。

## 1. 要做成什么

用户用一句话描述想要的队伍，例如「以皮卡丘为主力，参考前一天使用率最高的组合」。系统根据知识库配出一支 6 只的队伍。

知识库存放：

- 对战细则
- 每只洛克宠物的属性、特性、种族值、个体值、技能池、战斗风格
- 带时间的模拟使用率（前一天、上个月）
- 用户提供的完美配对，作为后续偏好学习的目标

三个助手各自给出多套方案，最后采用重合最多、并且符合人数、主力和技能池的那一套。

模型侧固定为：

| 项 | 选择 |
| --- | --- |
| 训练框架 | LLaMA-Factory |
| 微调算法 | LoRA |
| 基座模型 | Qwen-1.5B，具体权重用 `Qwen/Qwen2.5-1.5B-Instruct` |
| 模型接口 | FastAPI |
| 业务后端 | Spring Boot |
| 前端 | Vue 3 |

`Qwen/Qwen2.5-1.5B-Instruct` 是参数量约 15 亿的指令模型。Qwen1.5 系列没有名为 1.5B 的官方权重，实施时不要改成 Qwen1.5-1.8B。对话模板用 LLaMA-Factory 的 `qwen`。

智谱接口模型没有可训练权重。它如果继续使用，只负责生成老师轨迹，不参与 LoRA。

## 2. 现在已经有的部分

这些行为在拆服务时要保留，不推倒重写：

- 资料在 `knowledge/pokemon/*.json`、`knowledge/usage.json`、`knowledge/rules.md`、`knowledge/gold_teams.jsonl`
- 使用率助手、配合助手、诉求助手各写两套方案
- `choose_overlapping_scheme` 按共同成员选队，并跳过技能池或主力不合规的方案
- 核对员只检查被选中的那一套
- 用户采纳、拒绝和改写进入 `data/preferences/`，完美配对可变成优选答案
- 现有 FastAPI 已经有配队、反馈、会话和用户接口，Gradio 只是临时页面

接下来替换的是运行形态：Gradio 换成 Vue 3，业务数据改由 Spring Boot 管，微调从手写的 `train_lora.py` 换成 LLaMA-Factory。

## 3. 总体结构

浏览器只访问 Spring Boot。Spring Boot 管用户、知识和记录，需要配队或推理时再调用 FastAPI。FastAPI 管检索、三个助手、重合选队，以及加载 LoRA 后的 Qwen。LLaMA-Factory 不对外网服务，只在训练机器上读数据集、写适配器。

```text
Vue 3
  → Spring Boot（用户、洛克宠物、使用率、完美配对、反馈、任务记录）
      → FastAPI（检索、三个助手、重合选队、LoRA 推理）
          → Qwen2.5-1.5B-Instruct + LoRA 适配器

老师轨迹 / 用户修正 / 完美配对
  → LLaMA-Factory 数据集
      → LoRA 训练
          → adapters/team-lora
              → FastAPI 加载
```

端口约定：

| 服务 | 端口 | 说明 |
| --- | --- | --- |
| Vue 3 | 5173 | 开发服务器，生产构建交给 Spring 静态资源或单独的 Nginx |
| Spring Boot | 8080 | 浏览器唯一的业务入口 |
| FastAPI | 8000 | 只允许 Spring Boot 或本机调用 |

## 4. 三个进程各自负责什么

### Vue 3

页面只做交互，不写配队规则，也不直接调用 FastAPI。

- 配队对话：输入诉求，展示采用方案、重合成员、引用来源、核对是否通过
- 知识库：维护最多 30 只洛克宠物，编辑前一天和上个月的使用率，编辑对战细则
- 完美配对：录入「诉求 + 6 名成员」
- 反馈：这队可以、这队不行；不行时提交想要的队伍
- 训练状态：查看数据集条数和最近一次 LoRA 任务的状态，不在浏览器里跑训练

建议目录：`web/`，使用 Vite、Vue 3、Vue Router、Pinia。界面组件库在实施时再定，不影响接口。

### Spring Boot

Spring Boot 是业务后端，持有自己的数据库。它不加载模型，也不实现三个助手。

负责：

- 注册、登录、会话
- 洛克宠物、使用率、细则、完美配对的增删改查
- 保存每次配队请求、六套方案摘要、最终采用方案和核对结果
- 保存用户反馈，并标记能否成为训练样本
- 用 WebClient 调用 FastAPI
- 管理员触发「导出训练集」和「开始 LoRA」时，把请求转给 FastAPI，并记下任务状态

建议目录：`server/`，Java 17，Spring Boot 3。数据先用 MySQL；本地开发可以用 H2，表结构保持一致。

核心表：

| 表 | 内容 |
| --- | --- |
| `user` | 账号 |
| `pokemon` | 一只洛克宠物一份资料，对应现在的 JSON 字段 |
| `usage_window` | `yesterday` 或 `last_month`，以及日期 |
| `usage_entry` | 该窗口下的洛克宠物使用率和队伍使用率 |
| `battle_rule` | 细则正文 |
| `gold_team` | 诉求、6 名成员、备注 |
| `team_job` | 一次配队的输入、输出、重合说明、是否通过核对 |
| `feedback` | 采纳或拒绝、用户改写、对应的 `team_job` |
| `train_job` | 数据集路径、状态、适配器目录、错误摘要 |

现有 `knowledge/` 里的 8 只示例和模拟使用率，作为 Spring Boot 的初始数据导入进去。补满 30 只时走管理页面或导入接口，不把新资料写死在代码里。

### FastAPI

FastAPI 是模型接口，保留并收紧现在的 Python 能力。

负责：

- 从 Spring Boot 传来的资料构造检索片段。向量检索仍只处理额外上传的长文档；使用率、属性和技能池继续用结构化过滤，避免「前一天最高使用率」被向量搜索改写
- 调用三个助手，各生成两套方案，再用现有重合规则选队
- 加载 `Qwen/Qwen2.5-1.5B-Instruct` 和 LoRA 适配器，提供复现接口
- 把老师轨迹导出成 LLaMA-Factory 能读的数据集
- 在本机启动 LLaMA-Factory 训练，并报告进度

Gradio 的 `app.py` 在 Vue 可用后停用，不再作为正式入口。

## 5. 配队怎么走

一次用户请求的正式路径：

1. Vue 把诉求发给 Spring Boot。
2. Spring Boot 读出洛克宠物、当前窗口的使用率、细则，连同诉求、最近几轮对话一起交给 FastAPI。
3. FastAPI 的检索步骤只做整理：按「上个月 / 前一天」选择窗口，取出高使用率队伍和相关洛克宠物，附上细则。
4. 使用率助手、配合助手、诉求助手各自给出两套方案。
5. 重合选择沿用现在的规则：统计成员出现次数，优先采用共同成员多、包含点名主力、且技能池和人数合法的一套。
6. 核对员只检查这一套。结果返回 Spring Boot，Spring Boot 落库后再给 Vue。

三个助手在 LoRA 完成前，可以暂时调用外部大模型生成老师方案。LoRA 完成后，增加一种运行模式：检索结果不变，最终成文改为本地 Qwen 复现。两种模式都从 Spring Boot 的同一个配队接口进入，用字段 `mode` 区分：

- `agents`：三个助手加重合选队
- `lora`：本地模型按技能和检索片段复现配队

默认仍是 `agents`。`lora` 只有适配器文件存在时才允许调用。

## 6. LLaMA-Factory 与 LoRA

### 训练目标

学生模型要学会的是配队员技能，不是重新发明检索。输入里已经包含技能说明、检索片段和用户诉求。输出固定两段：

```text
【抽出的技能步骤】
1. ...
【复现结果】
【队伍】
- ...
【理由】
...
```

技能正文来自 `agents/skills/` 里对应助手的 `SKILL.md`。第一版只蒸馏「被重合选中的那套方案」所对应的助手技能。检索、使用率过滤和重合计票仍由程序完成，不放进 LoRA 的学习目标。

只有核对通过的轨迹进入训练集。用户改写过的队伍，以及 `gold_team` 里与模型答案不同的完美配对，作为下一阶段偏好数据，不和第一版 LoRA 监督样本混在同一个损失里。

### 数据格式

导出目录用 `data/llamafactory/`。样本使用 ShareGPT 消息格式，并在 `dataset_info.json` 注册：

```json
{
  "team_lora": {
    "file_name": "team_lora.json",
    "formatting": "sharegpt",
    "columns": {
      "messages": "messages"
    },
    "tags": {
      "role_tag": "role",
      "content_tag": "content",
      "user_tag": "user",
      "assistant_tag": "assistant",
      "system_tag": "system"
    }
  }
}
```

一条样本的三则消息：

- system：你是经过技能蒸馏的本地模型。先抽出技能步骤，再只根据检索片段完成配队。
- user：技能原文、检索片段、用户诉求。
- assistant：抽出的步骤，加上核对通过的队伍和理由。

导出由 FastAPI 的现有轨迹完成，替代现在的 `train_lora.py`。`train_dpo.py` 和 `train_ppo.py` 先留着，不作为这一版的训练入口。

### 训练配置

训练配置放在 `train/qwen1_5b_lora.yaml`，用 LLaMA-Factory 启动：

```bash
llamafactory-cli train train/qwen1_5b_lora.yaml
```

配置要点：

| 项 | 值 |
| --- | --- |
| `stage` | `sft` |
| `finetuning_type` | `lora` |
| `model_name_or_path` | `Qwen/Qwen2.5-1.5B-Instruct` |
| `template` | `qwen` |
| `dataset` | `team_lora` |
| `lora_rank` | 8 |
| `lora_alpha` | 16 |
| `lora_dropout` | 0.05 |
| `lora_target` | `q_proj,v_proj` |
| `cutoff_len` | 2048 |
| `per_device_train_batch_size` | 1 |
| `gradient_accumulation_steps` | 8 |
| `learning_rate` | 0.0001 |
| `num_train_epochs` | 3 |
| `output_dir` | `adapters/team-lora` |

没有可用 GPU 时不启动正式训练。1.5B 可以在单张消费级显卡上做 LoRA，CPU 只能用来检查数据集格式。训练产物是适配器目录，不默认把权重合并回基座，方便更换数据集后重训。

### 推理

FastAPI 启动时如果发现 `adapters/team-lora`，就用 LLaMA-Factory 的推理接口或同等的 `transformers + peft` 加载基座和适配器。对外只暴露业务接口，不把 LLaMA-Factory 自带的网页暴露到公网。

`lora` 模式的输入与训练时的 user 消息相同：技能、检索片段、诉求。返回文本再由程序检查人数、主力和技能池。检查失败时把问题返回前端，不把未通过的队伍伪装成最终结果。

## 7. 接口草案

Vue 只调用 Spring Boot 的 `/api`。下面是第一批需要实现的接口。

| 方法 | Spring Boot | 作用 |
| --- | --- | --- |
| POST | `/api/auth/register` | 注册 |
| POST | `/api/auth/login` | 登录 |
| GET | `/api/pokemon` | 洛克宠物列表 |
| PUT | `/api/pokemon/{name}` | 新增或更新一只洛克宠物 |
| GET | `/api/usage/{window}` | 读取前一天或上个月的使用率 |
| PUT | `/api/usage/{window}` | 更新该窗口 |
| GET / PUT | `/api/rules` | 读取或更新细则 |
| GET / POST | `/api/gold-teams` | 完美配对 |
| POST | `/api/teams/build` | 配队。正文含 `request` 和 `mode` |
| POST | `/api/teams/{id}/feedback` | 采纳、拒绝、改写 |
| POST | `/api/train/export` | 导出 LLaMA-Factory 数据集 |
| POST | `/api/train/lora` | 启动 LoRA 任务 |
| GET | `/api/train/{id}` | 查询训练状态 |

Spring Boot 调用 FastAPI 时使用内部接口：

| 方法 | FastAPI | 作用 |
| --- | --- | --- |
| POST | `/internal/teams/build` | 接收结构化知识、诉求和模式，返回方案、采用结果和核对 |
| POST | `/internal/lora/reproduce` | 用适配器复现配队 |
| POST | `/internal/train/export` | 从已通过轨迹写出 `team_lora.json` |
| POST | `/internal/train/lora` | 启动 `llamafactory-cli train` |
| GET | `/internal/train/{id}` | 训练是否结束、适配器路径、错误摘要 |

现有 `/api/v1/agents/query` 的行为由 `/internal/teams/build` 承接。对外 Gradio 和浏览器不再直接访问 8000 端口。

`/api/teams/build` 的响应至少包含：采用方案正文、重合成员及出现次数、六套方案的成员列表、核对是否通过、引用来源、`team_job` 编号。

## 8. 建议目录

实施时在现有仓库里增加这些目录，不把 Python 配队代码搬进 Java。

```text
web/                  Vue 3
server/               Spring Boot
train/                LLaMA-Factory 的 yaml 与 dataset_info.json
adapters/team-lora/   训练产物，不提交大文件
data/llamafactory/    导出的 team_lora.json，不提交
knowledge/            继续保留示例数据，供导入
agents/               继续保留三个助手技能和选队流程
```

`adapters/` 和 `data/llamafactory/` 放进 `.gitignore`。

## 9. 实施顺序

按这个顺序做，每一步都能单独看结果。

1. 定 Spring Boot 表结构，并把当前 `knowledge/` 导入数据库。配队规则先不改。
2. 做 Vue 的配队页和知识库页，先由 Spring Boot 返回假数据，确认页面字段。
3. Spring Boot 把数据库中的资料转给现有 FastAPI 配队流程，Vue 能完成一次真实的三助手重合配队。
4. 反馈和完美配对写入 Spring Boot，并能够导出 ShareGPT 文件。
5. 用少量已通过样本跑通 LLaMA-Factory 的 LoRA 配置，确认损失下降、适配器可以加载。
6. FastAPI 增加 `lora` 复现接口，Spring Boot 和 Vue 增加模式切换。
7. 样本积累后，再单独立项用 LLaMA-Factory 的 DPO 读取偏好对。PPO 不放进这一版，因为 1.5B 的在线采样成本高，而且当前奖励已经能由规则计分，不需要先上 PPO。

## 10. 这一版不做什么

- 不改现在的重合选队规则，也不把三个助手合并成一次生成
- 不在 Vue 或 Spring Boot 里重写属性克制和技能池检查
- 不用 LoRA 去微调智谱接口模型
- 不把适配器合并进基座后再提交到 Git
- 不在方案确认前安装 LLaMA-Factory、创建 Vue 工程或 Spring Boot 工程
